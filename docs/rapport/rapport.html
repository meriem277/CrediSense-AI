1. En bref

CrediSense AI reçoit les pièces d'un client (CIN, fiche de paie, relevé bancaire, attestation de travail…), les lit par OCR, en extrait les données, puis calcule si le crédit demandé est supportable. Le client dépose sa demande sur un portail. Un agent de la banque vérifie les documents, lance l'analyse et obtient un résultat expliqué : décision, contrôles réglementaires, capacité d'emprunt, simulations de durée, points forts et points de vigilance.

Le projet tourne en production sur une machine virtuelle Azure, déployée par Terraform et Docker Compose, derrière un reverse proxy HTTPS.

3. Le pipeline de A à Z

Le pipeline a deux acteurs : le client dépose, l'agent vérifie puis analyse. Chaque étape a un point d'entrée précis dans le code.

A

Le client crée sa demande

Le portail client (/client/demande) envoie le montant, la durée et le type de contrat à POST /api/public/demande. Un dossier est créé en base avec le statut EN_ATTENTE.

B

Le client dépose ses pièces

POST /api/public/upload (DemandeCreditController). Le nom du fichier et le CIN sont assainis, le fichier est écrit dans upload.base-path (volume persistant /data/uploads), puis une ligne Fichier est créée avec le type de document choisi par le client (« AUTRE » par défaut).

C

L'agent ouvre le dossier

L'espace agent charge les fichiers (GET /api/dossiers/{id}/fichiers). Chaque document porte son statut OCR (ocrStatut, ocrErreur), son JSON extrait et sa cohérence de CIN. Le composant pipeline-analyse affiche quatre étapes : documents, cohérence du CIN, analyse, score.

D

Étape 1 : « Vérifier les documents »

POST /api/fichiers/verifier-dossier/{id} → verifierDossier() → lireEtExtraire().

  1. Saut des documents déjà traités : un document est « déjà vérifié » s'il a un texte OCR réussi et une extraction non vide. Il n'est ni relu ni renvoyé au LLM.
  2. OCR : le backend envoie le fichier au service IA (POST /ocr). Le format est détecté par les premiers octets du fichier (PDF, JPG, PNG, TIFF, BMP, WebP). Un PDF natif est lu directement avec PyMuPDF. Un scan ou une photo passe par PaddleOCR : détection des zones, lecture par le modèle arabe et par le modèle latin, fusion zone par zone, regroupement par ligne, normalisation Unicode. Le Word et le HEIC sont refusés avec un message explicite.
  3. Enregistrement : ocr_results reçoit le texte, le statut (SUCCESS ou FAILED) et la raison de l'échec.
  4. Classification : le texte est envoyé à POST /ai/classify-hybrid avec le type déclaré par le client. Le service renvoie le type détecté, sa confiance, la méthode, et un bloc « contrôle » : concordant, en désaccord, ou sans conclusion (section 4). Le résultat est enregistré sur le fichier (typeDetecte, confianceType, methodeType, typeConflit). Si la classification tombe en panne, le pipeline continue avec le type déclaré.
  5. Extraction JSON adaptée au type : le texte est envoyé à POST /ai/extract-json avec le type retenu (le type détecté s'il est fiable, sinon le type déclaré). Le schéma demandé au LLM et les consignes dépendent de ce type : une CIN ne demande que nom, prénom et numéro ; une fiche de paie demande le « net à payer » et pas le brut ; un relevé demande les échéances de crédit et les incidents. Le résultat est validé par Pydantic, avec un score de confiance selon le type. Une extraction vide ou en échec n'est pas enregistrée : le document ne peut donc pas être « validé » à tort.
  6. Cohérence du CIN : toResponse() compare, en chiffres uniquement, le CIN extrait de chaque document au CIN du client. Résultat : cohérent, incohérent ou sans objet (justificatif de domicile par exemple).
E

Verrou : le bouton « Analyser »

Il n'est actif que si les étapes 1 et 2 sont valides. Si seul le CIN est incohérent, ou si le contenu d'un document ne correspond pas à son type déclaré, l'agent peut continuer après une confirmation explicite (il a vérifié à la main). Le serveur applique la même règle : POST /api/fichiers/analyser-dossier/{id} répond 409 (CIN_INCOHERENT ou TYPE_INCOHERENT) sans le paramètre confirmerIncoherence=true. Une seule confirmation couvre les deux cas. Aucun appel LLM n'est gaspillé sur un dossier douteux.

Après la confirmation, le pipeline passe au vert. Le contrôle manuel de l'agent vaut validation : les étapes « Vérification CIN » et « Validation des documents » deviennent vertes avec la mention « incohérence confirmée manuellement par l'agent ». C'est vrai aussi à la réouverture d'un dossier déjà analysé, puisque le serveur refuse d'analyser un dossier incohérent sans confirmation. La confirmation ne masque rien d'autre : un nom manquant sur la CIN ou un document requis absent restent en erreur.

F

Étape 2 : « Analyser » (analyserEtScorer())

  1. Relit uniquement ce qui manque (normalement rien).
  2. Indexe les textes pour le chatbot (POST /ai/chat/index), sans appel LLM.
  3. Assemble le texte du dossier avec un en-tête par document (=== TYPE (nom) ===, avec le type détecté quand il contredit le type déclaré) et ajoute en tête la demande du client (montant, durée, contrat), absente de tous les documents.
  4. Vérifie l'identité : le nom et le prénom du client dans le dossier sont comparés à ceux lus dans les documents (alerteIdentite). Cette vérification relance une extraction LLM sur le texte complet du dossier.
  5. Appelle le scoring : POST /ai/score/consommation.
G

Le scoring dans le service IA (AgentService.analyser_consommation)

  1. Cache : la clé contient le texte, la version des règles, le taux et la taille maximale. Changer l'un d'eux ne ressert jamais une ancienne analyse.
  2. Budget de texte : 12 000 caractères répartis équitablement entre les documents. Un document trop long garde son début et sa fin. Aucun document n'est supprimé. Un avertissement signale tout raccourcissement.
  3. Un seul appel LLM (tâche « analyse », température 0,1, JSON imposé) : il lit le dossier et propose revenus, contrat, ancienneté, dettes, points forts, risques, plan, score et décision. Le JSON tronqué est réparé automatiquement.
  4. Dettes : détecteur par règles dans le relevé bancaire (dettes_releve.py) et valeur lue par le LLM. On garde la plus élevée, avec un avertissement en cas d'écart. Un « 0 » sans relevé lisible n'est pas une preuve : la dette reste inconnue.
  5. Couche déterministe (appliquer_regles) : le LLM n'a plus la main sur les chiffres. Mensualité, taux d'endettement (DTI), capacité d'emprunt et simulations sont recalculés en Python (section 4).
  6. Garde-fous : un critère bloquant en échec ramène « ELIGIBLE » à « CONDITIONNEL » (score plafonné à 59). Des données indispensables manquantes transforment toute décision favorable en « À COMPLÉTER ».
H

Sauvegarde et statut

Le backend enregistre : AgentAnalysis (score, revenus, endettement, décision), DecisionFinale (justification, message au client, résultat complet en JSON) et met à jour le statut du dossier : ELIGIBLE → APPROUVE, REFUS → REFUSE, toute autre décision → EN_COURS.

Envoi automatique de la réponse. Juste après l'enregistrement de la décision (étape H), NotificationDecisionService envoie au client l'e-mail de réponse avec le rapport PDF version client en pièce jointe.
  • Contrôle humain : un refus attend la validation d'un agent avant de partir (voir la section 4) ; les autres décisions partent immédiatement, ou après un délai annulable si on en configure un.
  • Décisions notifiées : éligible, refus, conditionnel, « à compléter » (qui demande au client les pièces manquantes). Une analyse échouée techniquement (INDETERMINE) n'envoie rien.
  • Pas de doublon : relancer l'analyse sans que la décision change ne renvoie pas d'e-mail ; si elle change (« à compléter » puis « éligible »), le client reçoit la nouvelle.
  • Un échec ne casse rien : l'erreur est enregistrée et affichée à l'agent, l'analyse est rendue normalement, et l'envoi est retenté à l'analyse suivante ou par le bouton « Envoyer la réponse au client ».
  • Interrupteur : AUTO_ENVOI_EMAIL=false coupe l'envoi automatique ; le bouton manuel reste.
  • L'e-mail part du résultat enregistré, pas de ce que le navigateur envoie : un appel falsifié ne peut pas changer ce que reçoit le client.
I

Résultat pour l'agent et le client

L'écran de résultat (credit-result) affiche la décision, le score (marqué « provisoire » si des données manquent), la liste des données manquantes, les contrôles réglementaires, la capacité, les simulations par durée, les points forts, les points de vigilance, les conditions et le taux utilisé. POST /api/dossiers/{id}/send-result-email envoie au client un message adapté à la décision. Pour « À COMPLÉTER », il ne cite que des pièces que le client peut fournir, jamais un réglage technique.

Le chatbot (POST /api/chatbot/question → /ai/chat) répond aux questions de l'agent sur le dossier par recherche dans les documents indexés (RAG), avec masquage des RIB, IBAN et CIN.

4. Le moteur de décision

Qui fait quoi : le LLM et les règles

L'« agent IA » est un appel LLM suivi de règles déterministes. Ce n'est pas un agent autonome avec des outils. Le LLM lit les documents. Les règles calculent et contrôlent. Ce partage est volontaire : un chiffre financier doit être reproductible et vérifiable.

Formules

  • Mensualité : annuité constante, M = C × i / (1 − (1 + i)^−n), avec i = taux annuel / 12.
  • Taux d'endettement (DTI) : (mensualité + dettes mensuelles) / revenu net × 100.
  • Mensualité maximale : 30 % × revenu − dettes. Le montant finançable en découle (inverse de la formule d'annuité), plafonné à 5 × le salaire.
  • Simulations : durées 12, 24, 36, 48, 60 et 84 mois, plus la durée demandée. Pour chacune : mensualité, DTI, coût total, statut.

La classification des documents

Problème. Le type d'un document vient de l'emplacement choisi par le client à l'upload. Un relevé bancaire déposé dans « fiche de paie » serait traité comme une fiche de paie : revenu et dettes faux. La classification vérifie la nature réelle du document.

Cascade à trois niveaux (DocumentClassifierService) :

NiveauFonctionnementCoût
0. RèglesMots-clés par type, en trois forces : titres (« ATTESTATION DE TRAVAIL », « BULLETIN DE PAIE »…), forts et faibles. Le poids d'un titre dépend de sa position : plein poids tout en haut du texte, poids réduit plus bas. Une attestation qui cite « la carte d'identité nationale » n'est donc pas classée CIN. Texte normalisé (sans accents ni voyelles arabes), français et arabe. Les règles répondent seulement si le verdict est net (score ≥ 5 et écart ≥ 3), sinon elles s'abstiennent, et ne répondent jamais « AUTRE ».instantané, gratuit, reproductible
1. EmbeddingsSimilarité sémantique (MiniLM multilingue) avec des phrases de référence. Si la similarité dépasse 0,55, verdict retenu.quelques ms, local
2. LLMSeulement dans la zone grise (similarité entre 0,20 et 0,55). Si le LLM est indisponible, on garde le verdict des embeddings.un appel LLM, rare

Contrôle déclaré / détecté (controle_type.py). On ne signale un conflit que si le verdict est fiable. Chaque méthode a son seuil : règles 0,80, embeddings 0,55, LLM 0,70 (leurs échelles de confiance ne sont pas comparables). Un verdict incertain, « AUTRE » ou un type non déclaré ne produit jamais de conflit : il ne bloque rien. En cas de conflit fiable, le type détecté pilote l'extraction JSON et le texte vu par l'IA de scoring ; le type déclaré n'est pas écrasé.

Choix de conception. Un désaccord bloque « Analyser » jusqu'à confirmation de l'agent, comme pour le CIN : la banque garde la main, et aucune correction automatique n'est faite.

Traçabilité : le popup « Détail de la classification »

L'agent doit pouvoir voir exactement ce qui s'est passé. Le service IA renvoie donc, avec chaque verdict, la trace de la cascade niveau par niveau : consulté ou non, a tranché ou non, et pourquoi. Le backend la conserve sur le document (colonne classificationJson) et l'écran l'affiche.

  • Sur chaque document : une ligne lisible sans rien ouvrir, par exemple « Détecté : Relevé bancaire · règles par mots-clés · confiance 90 % ». Une similarité d'embeddings est affichée comme telle (« similarité 0,56 »), jamais comme un pourcentage.
  • Popup (bouton « Détail de la classification ») : type déclaré, type détecté, type utilisé pour l'extraction, verdict (conforme, contradiction, sans conclusion, type complété), puis les trois niveaux :
    • Règles : mots-clés reconnus, classement des candidats avec leurs scores, seuils à atteindre.
    • Embeddings : meilleur candidat, similarité, seuil, candidats.
    • LLM : réponse, confiance, justification, fournisseur ; ou « indisponible » avec la raison.
    Un niveau non consulté est indiqué comme tel, avec la raison (« les règles ont tranché »). Le popup montre aussi le CIN lu dans le document face au CIN du client.

Contrôle humain avant l'envoi de la réponse

Problème. L'envoi automatique faisait partir un refus chez le client dès que l'IA avait tranché, alors que le score vient du modèle de langage. Une banque veut qu'un humain puisse relire avant.

Garde-fou. « Valider » envoie au serveur la décision que l'agent a sous les yeux. Si une nouvelle analyse l'a changée entre-temps, le serveur répond 409 et n'envoie rien : le client ne reçoit jamais autre chose que ce qui a été relu. L'écran relit alors l'état réel du dossier.

Réglages (variables d'environnement du backend) : VALIDATION_REQUISE_POUR (liste de décisions, par défaut REFUS ; vide : aucune), DELAI_ENVOI_MINUTES (par défaut 0), AUTO_ENVOI_EMAIL (couper tout l'automatique).

La date d'une décision est celle de la dernière décision (champ dédié) : une nouvelle analyse met à jour la même ligne, et un horodatage automatique bougerait à chaque changement d'état de l'e-mail et fausserait les délais.

Le chatbot RAG : indexation, découpage, recherche

RAG (Retrieval-Augmented Generation) : on ne donne pas tout le dossier au LLM à chaque question. On cherche d'abord les passages utiles, puis on les lui donne avec la question. Fichier principal : chatbot_service.py.

Indexation = préparer les documents pour qu'on puisse les chercher vite, comme l'index d'un livre. Elle se fait une fois par analyse : (1) découper les textes OCR en chunks, (2) transformer chaque chunk en vecteur de 384 nombres avec le modèle d'embedding (MiniLM multilingue), (3) ranger les vecteurs dans FAISS (IndexFlatIP, recherche exacte par cosinus), plus un index lexical BM25. Les index sont en mémoire, un par dossier ; les textes viennent de PostgreSQL (ocr_results).

Découpage structurel et sémantique (decoupage_rag.py)

Type de texteDécoupage
Relevé bancaireUn chunk par opération (une ligne datée). Chaque chunk répète l'en-tête « Date | Libellé | Débit | Crédit | Solde », et le sens crédit / débit est déduit du solde (ancien solde + montant = nouveau solde : crédit). Si le solde ne colle pas, aucun sens n'est inventé.
Document court (CIN, attestation…)Un seul chunk : il n'est jamais coupé.
Texte libreCoupure aux changements de sujet (semantic chunking) : pour chaque frontière, on compare la moyenne des embeddings des 2 lignes avant à celle des 2 lignes après, et on coupe aux frontières dont la similarité est parmi les plus basses.
TousTaille maximale de 450 caractères, ce que le modèle lit réellement (128 tokens). Une coupure forcée par la taille garde une ligne de chevauchement ; une coupure sémantique n'en a pas besoin.

Avant, le découpage était positionnel (2 lignes avant, 3 après) : sur un relevé, une opération était coupée et les montants perdaient leur en-tête de colonnes.

Recherche hybride (recherche_hybride.py)

  • Sens : FAISS compare le vecteur de la question à ceux des chunks. « salaire » retrouve « NET A PAYER », en français comme en arabe.
  • Mots exacts : BM25 (écrit en Python pur, sans dépendance) retrouve les montants, noms et numéros que les embeddings pèsent mal. Un montant « 2 100,000 » donne les jetons « 2100 » et « 2100000 ».
  • Fusion RRF (Reciprocal Rank Fusion) : un chunk bien classé par l'une OU l'autre remonte.
  • Couverture : au moins 2 chunks de chaque document, puis complément jusqu'à 12 chunks.

Mémoire de conversation

Problème. Chaque question était traitée seule. À « Et depuis quand ? », le modèle ne savait pas de quoi on parlait, et surtout la recherche non plus : une relance ne contient aucun mot utile pour trouver les bons passages.

  1. Envoi de l'historique : Angular garde déjà les messages et envoie maintenant les 6 derniers échanges réels avec chaque question (sans la salutation ni les messages d'erreur, qui n'ont pas été dits au modèle). Le contrôleur Java les transmet à /ai/chat.
  2. Historique donné au LLM : les tours précédents sont insérés au format chat (system, user, assistant, user), tronqués à 6 messages de 600 caractères. Le prompt système précise que l'historique sert à comprendre la question de suivi et n'est pas une source de vérité : une valeur citée plus tôt n'est une donnée du dossier que si elle figure aussi dans le contexte.
  3. Question de recherche complétée : une question « relance » (courte, commençant par « et », « mais », « pourquoi »…, ou contenant « précédent », « même », « cela »…) est cherchée avec la ou les questions précédentes de l'agent. C'est une règle, sans appel LLM de plus.
  4. Sécurité de l'historique : il vient du navigateur, donc il n'est pas cru. Seuls les rôles « user » et « assistant » sont gardés (un faux message « system » est ignoré), les CIN, RIB et IBAN sont masqués, les messages sont tronqués. Le nettoyage est fait côté Java et refait côté Python, qui fait foi.

Résultat mesuré (vrai modèle MiniLM, après « Y a-t-il une échéance de prêt prélevée ? ») : la relance « Et depuis quand ? » ramenait sans mémoire l'attestation d'emploi (hors sujet) ; avec mémoire elle retrouve les trois prélèvements du prêt dans le relevé.

Génération et garde-fous

Les 12 chunks sont envoyés au LLM étiquetés « [Source 3 : Fiche de paie] ». CIN, RIB et IBAN sont masqués avant l'envoi et dans la réponse. Le prompt impose de ne répondre que sur le dossier, de traiter toute donnée absente du contexte comme une hypothèse, et de lire correctement les montants tunisiens (« 4 800,000 » vaut 4800 DT).

Le détecteur de dettes (dettes_releve.py)

Il lit le texte du relevé, regroupe les opérations par date (un PDF natif met chaque cellule du tableau sur une ligne séparée), repère les mots d'échéance de prêt sur du texte sans accents, exclut salaire, total et solde, et retient le plus fort total mensuel des deux derniers mois. Une échéance déjà soldée n'est plus comptée.

Limite assumée. C'est une heuristique sur du texte. Le résultat est toujours présenté comme « détecté, à confirmer ».

8. Speech : présenter l'architecture (environ 4 minutes)

Ouverture. Bonjour. Je vais vous présenter CrediSense AI, une application qui aide un conseiller bancaire à étudier une demande de crédit à la consommation. Le problème de départ est simple : un dossier arrive avec cinq ou six documents, souvent scannés, en arabe et en français, et le conseiller doit tout relire pour savoir si le client peut rembourser. Notre application fait cette lecture et ce calcul, puis explique son résultat.

Les trois blocs. L'architecture tient en trois blocs. Devant, une application Angular : un portail où le client dépose sa demande et ses pièces, et un espace où le conseiller travaille. Au milieu, un backend Spring Boot. C'est le chef d'orchestre : il gère les comptes, les dossiers, les fichiers, et il décide de l'ordre des étapes. Derrière, un service d'intelligence artificielle en Python avec FastAPI. Lui, il sait lire les documents, extraire les informations et faire l'analyse. Une base PostgreSQL garde tout, et un reverse proxy, Caddy, protège l'ensemble avec le HTTPS.

Pourquoi séparer le backend et le service IA. C'est un choix volontaire. Le monde de l'IA, avec PaddleOCR et les modèles, vit en Python. Le monde métier, avec la sécurité, les transactions et la base de données, est solide en Java. Chacun reste dans son langage et peut être déployé et mis à jour séparément. Ils se parlent par des appels HTTP simples, dans un réseau privé.

Le parcours d'un dossier. Le client dépose ses pièces. Le conseiller clique sur « Vérifier les documents ». À cet instant, chaque document passe par l'OCR : si le PDF contient déjà du texte, on le lit directement ; si c'est un scan ou une photo, PaddleOCR lit le texte avec deux modèles, un arabe et un français, puis on fusionne les deux lectures. Ensuite un modèle de langage transforme ce texte en données structurées : nom, CIN, salaire, type de contrat, avec des consignes adaptées au type de document. Et le système vérifie que le CIN lu sur chaque document est bien celui du client.

Le verrou. L'analyse ne démarre que si cette vérification est valide. Si le CIN ne correspond pas, le conseiller peut continuer, mais seulement en confirmant explicitement, et le serveur refuse de lui-même sans cette confirmation. Nous ne dépensons donc pas un appel d'IA sur un dossier qui n'est peut-être pas le bon.

Le contrôle des documents. Le client choisit lui-même où il dépose chaque pièce. Rien ne l'empêche de mettre un relevé bancaire à la place de la fiche de paie. Nous vérifions donc la nature réelle de chaque document, avec une classification en trois niveaux. D'abord des règles : le titre du document, « attestation de travail », « bulletin de paie », « relevé de compte », en français comme en arabe. C'est instantané, gratuit et reproductible. Si les règles ne sont pas sûres, on passe à une comparaison sémantique par embeddings, et seulement en dernier recours à un modèle de langage. Nous avons ajouté les règles après une mesure : les embeddings seuls classaient une attestation de travail comme une carte d'identité, parce qu'elle cite le numéro de carte. Si le contenu contredit l'emplacement choisi, l'analyse est bloquée jusqu'à ce que le conseiller confirme, et le type réel sert aussi à adapter l'extraction : on ne demande pas les mêmes champs à une carte d'identité et à un relevé.

Le chatbot. Le conseiller peut aussi poser des questions en langage naturel sur le dossier. Nous utilisons une architecture RAG : les documents sont découpés, transformés en vecteurs par un modèle d'embedding multilingue, et rangés dans un index. À chaque question, on retrouve les passages les plus proches, par le sens et par les mots exacts, puis un modèle de langage rédige la réponse en citant ses sources. Le découpage tient compte de la structure : un relevé bancaire est coupé par opération, avec ses en-têtes de colonnes, parce qu'un montant n'a de sens qu'avec sa colonne. Le chatbot a aussi une mémoire de conversation : le conseiller peut enchaîner « Et depuis quand ? » sans répéter le sujet, parce que la relance est complétée avec la question précédente avant la recherche.

Le cœur : un agent en deux couches. Pour l'analyse, nous avons fait un choix important. Le modèle de langage lit le dossier et propose une première évaluation. Mais il ne calcule pas les chiffres. Les mensualités, le taux d'endettement, la capacité d'emprunt et les simulations sont calculés par des règles, en Python, avec des formules connues. Ces règles contrôlent aussi les critères réglementaires : endettement sous 30 %, montant plafonné à cinq fois le salaire, durée, ancienneté. Si le modèle dit « éligible » alors qu'un critère bloquant échoue, les règles corrigent. Un chiffre financier doit être reproductible, et on peut l'expliquer.

L'honnêteté du calcul. Dernier point, et c'est celui dont je suis le plus fier : le système ne devine jamais. Si le taux d'intérêt n'est pas configuré, il ne calcule aucune mensualité. Si on ne sait pas si le client a déjà un crédit, il ne suppose pas que non : il détecte les échéances dans le relevé bancaire, et s'il n'y a pas de relevé, la dette reste inconnue. Dans ces cas, la décision n'est ni « éligible » ni « refus », c'est « à compléter », avec la liste précise de ce qu'il manque.

Déploiement. Tout tourne sur une machine virtuelle Azure, créée avec Terraform, donc reproductible. Les cinq services sont des conteneurs Docker orchestrés par Docker Compose. Les fichiers déposés et la base sont sur des volumes persistants, donc ils survivent aux mises à jour. Le code est construit et publié automatiquement par GitHub Actions.

Ce qui reste à faire, et je préfère le dire. Le score affiché vient encore du modèle de langage ; nous préparons une grille de score déterministe. La classification est en place, mais nous ne connaissons pas encore sa précision réelle : nous l'avons mesurée sur nos propres documents de test, ce qui est optimiste. Il nous faut de vrais documents de la banque pour la valider. Côté sécurité, plusieurs routes doivent encore être protégées avant un usage réel. Et le taux d'intérêt doit être fourni par la banque.

Conclusion. En résumé : une architecture à trois couches claire, un pipeline verrouillé étape par étape, un calcul que l'on peut expliquer, et un système qui préfère dire « il me manque une information » plutôt que d'inventer une réponse. Merci, je suis prêt pour vos questions.

QuestionRéponse
Pourquoi un LLM et des règles ?Le LLM comprend des documents variés. Les règles garantissent des calculs reproductibles et conformes. Chacun fait ce qu'il fait bien.
Est-ce vraiment un « agent » ?Non au sens autonome. C'est un appel LLM suivi d'une couche de règles. Le pipeline orchestré par le backend joue le rôle de l'agent.
Que se passe-t-il si le LLM est saturé ?Bascule automatique Groq / Mistral. Si tous échouent, la décision est « indéterminée » avec un message clair, sans bloquer le dossier.
Que se passe-t-il si un document est illisible ?Le statut OCR « FAILED » et sa raison s'affichent sur le document. Aucune extraction vide n'est enregistrée comme valide.
Comment gérez-vous l'arabe ?Deux lectures de la même zone, par un modèle arabe et un modèle latin, fusionnées zone par zone.
Les données personnelles sont-elles protégées ?Le chatbot masque RIB, IBAN et CIN, et les journaux n'affichent plus le texte OCR. Les routes API doivent encore être protégées : c'est notre priorité de sécurité.
Quelle est la précision ?Calculs : déterministes et testés. Classification : 10 documents sur 10 avec les règles sur notre dossier de test, mais ce dossier est écrit par nous, donc le chiffre est optimiste ; sur les embeddings seuls, 3 sur 5. La vraie précision se mesurera avec des documents réels de la banque. Score : celui du LLM, non mesuré pour l'instant.
Un refus peut-il partir sans qu'un humain l'ait vu ?Non par défaut : un refus attend « Valider et envoyer » de l'agent, qui peut aussi décider de ne pas l'envoyer. La validation porte sur la décision lue : si une nouvelle analyse l'a changée, le serveur refuse. Les autres décisions peuvent partir seules ou après un délai annulable, c'est réglable.
Comment prouvez-vous qui a décidé quoi ?Un journal d'audit en ajout seul : chaque analyse (décision, score, version des règles, fournisseur d'IA) et chaque étape de la réponse (mise en attente, validation, annulation, envoi, échec) est consignée avec l'agent et l'heure. Aucune route ne permet de le modifier.
Que montre le tableau de bord ?Taux d'acceptation (éligibles ÷ décisions définitives, avec une version « avec conditions »), répartition des décisions, délais de traitement et d'envoi, motifs de refus, évolution dans le temps et état des envois, avec un export Excel. Les définitions sont affichées à l'écran.
Comment fonctionne votre RAG ?Indexation : découpage structurel et sémantique, embeddings MiniLM multilingue, index FAISS en mémoire plus BM25. Question : recherche hybride (sens plus mots exacts) fusionnée par RRF, au moins 2 passages par document, puis génération par le LLM avec sources citées et identifiants masqués.
Comment gérez-vous la mémoire du chatbot ?Le navigateur renvoie les 6 derniers messages avec chaque question. Le modèle les reçoit comme historique de conversation, et une question de suivi est complétée avec la question précédente pour la recherche, par une règle simple qui n'ajoute aucun appel LLM. L'historique n'est pas cru : rôles filtrés, identifiants masqués, messages tronqués.
Pourquoi une recherche hybride ?Les embeddings comprennent le sens mais pèsent mal les valeurs exactes. Sur « 250,000 », la similarité sémantique n'est que de 0,27, alors que BM25 retrouve immédiatement l'opération. Les deux sont complémentaires.
Que se passe-t-il si le client dépose le mauvais document ?La classification le détecte, le pipeline affiche « déposé comme fiche de paie, le contenu ressemble à relevé bancaire », et « Analyser » reste bloqué jusqu'à ce que le conseiller confirme. Si la classification n'est pas sûre, elle ne bloque rien.
